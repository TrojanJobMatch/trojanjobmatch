TROJAN JOBMATCH - ARCHITECTURE
==============================

This describes the architecture as the code implements it. The README is
behind the code: it does not mention the "Evaluate my resume" feature or
lib/check/.


1. SYSTEM OVERVIEW
------------------

Trojan JobMatch is a single Next.js 16 App Router app (React 19, Tailwind 4)
deployed on Vercel. There is no separate backend: API route handlers talk
directly to Neon Postgres over HTTP and to Gemini over REST.

    Browser (client components, fetch)
       |
       v
    proxy.ts -- JWT cookie check, redirects to /login
       |        guards /dashboard, /check, /resume-builder, /api/dashboard/*
       v
    app/api/* route handlers -- each re-verifies the session (requireSession)
       |                 |                    |
       v                 v                    v
    lib/db.ts        lib/ai/gemini.ts     lib/check/* (pure TS, no AI)
    Neon Postgres    Gemini REST          PDF parsing + deterministic checks
    (HTTP driver)    (no SDK)             (unpdf / pdf.js)

Other external pieces: Gmail SMTP through nodemailer (password-reset emails)
and Google Identity Services (sign-in).

Environment variables: DATABASE_URL, SESSION_SECRET, GEMINI_API_KEY,
GEMINI_MODEL (optional), SMTP_USER, SMTP_PASS, NEXT_PUBLIC_GOOGLE_CLIENT_ID.


2. LAYERS
---------

Pages         app/*/page.tsx
              9 pages. Six are "use client"; the other three are a redirect
              (/), a static page (/privacy) and a wrapper around the client
              DashboardShell (/dashboard). Data is fetched from the API
              after mount; no server components do data work.

UI            components/{auth,dashboard,check,resume,brand,login}
              Presentational and stateful components. State is local
              useState; there is no store.

API           app/api/**/route.ts
              19 route files exporting 25 method handlers. Validation, SQL
              and AI orchestration are inline.

Domain logic  lib/auth       session/JWT, passwords, user rules, mail
              lib/ai         Gemini client, Analyst, agent tools
              lib/check      PDF reading, deterministic checks, check agents
              lib/dashboard  job domains, filter and feed types
              lib/resume     resume-builder data types and styles

Data          scripts/schema.sql, lib/db.ts
              Raw tagged-template SQL. No ORM, no migrations.

4. DATA MODEL
-------------

jobs                 The shared feed, loaded externally.
                     scripts/classify_jobs.ts tags each row with tm_domain,
                     tm_level and tm_type using the regexes in
                     lib/dashboard/domains.ts.

tm_users             Email, bcrypt hash (null for Google-only accounts),
                     google_sub, skills text[], department, photo (data URL).

tm_decisions         One row per (user, job): saved / applied /
                     not_interested.

tm_resumes           One per user: PDF bytes (bytea), extracted text, and the
                     AI-built profile JSON.

tm_analyses          Cached Analyst result per (user, job). Wiped when the
                     resume changes.

tm_resume_drafts     One resume-builder draft per user (style + JSON).

tm_checks            History of recruiter checks: analysis JSON, cache_key.

tm_password_resets   SHA-256 of the emailed token, 30-minute expiry, single
                     use.

tm_email_codes       Defined in the schema but never referenced by any code.

Everything per-user is keyed by the user_id taken from the session. No route
accepts a user id from the client.


5. AUTH
-------

Session
    HS256 JWT (jose) in the httpOnly cookie "trojanmatch_session"; sub is the
    user id. With "Keep me logged in" it lasts 30 days; otherwise the token
    lasts 12 hours and the cookie ends with the browser session.

Two-tier guard
    proxy.ts is the optimistic redirect. Every handler outside /api/auth
    also calls requireSession() itself. /api/agent, /api/resume, /api/check and /api/me
    are not in the proxy matcher and rely only on the handler check.

Sign-in flows
    - Password signup and login (bcryptjs, cost 12).
    - Google: the browser posts an ID token; the server verifies it against
      Google's JWKS (issuer, audience, email_verified), then finds or creates
      the user, linking by email.
    - Forgot/reset: random token emailed, only its SHA-256 stored, claimed
      atomically with a single UPDATE.

Stateless
    Logout only deletes the cookie. There is no server-side revocation.


6. AI SUBSYSTEM
---------------

lib/ai/gemini.ts is the single choke point. It tries gemini-flash-lite-latest
three times, then falls back to gemini-flash-latest, with a 25-second timeout
per attempt. geminiJSON forces JSON output at temperature 0.2.

6.1 Resume Reader (POST /api/resume)
    unpdf extracts text and links, Gemini builds the profile, and the
    extracted skills overwrite tm_users.skills.

6.2 Analyst (lib/ai/analyze.ts)
    One prompt comparing the resume with one job. Returns fit, eligibility,
    strengths, gaps and next steps. Cached in tm_analyses.

6.3 JobMatch Agent (POST /api/agent)
    A Gemini function-calling loop of up to 5 tool rounds, plus a final round
    with no tools to force a text answer.

    The six tools in lib/ai/agentTools.ts are presented as personas:
        Scout          search_jobs
        Resume Reader  get_my_profile
        Analyst        analyze_job
        Tracker        list_my_jobs, save_job, hide_job

    It is one model with one system prompt, not separate agents. Chat history
    lives in the browser (the last 6 turns are sent back) and nothing is
    stored server-side.

6.4 Recruiter check (POST /api/check)
    The most elaborate pipeline. Streamed to the browser as NDJSON, one line
    per stage.

    stored PDF bytes
        |
        v
    readPdf: rebuilds visual lines from x/y positions, collects links,
             metadata, and tiny or off-page text
        |
        v
    runDeterministic (no AI, milliseconds)
        hygiene, sections -> line ids, skill evidence, copied phrases,
        style flags, ATS checks, stuffing level
        |   stage: deterministic
        |
        +--------------------------+
        v                          v
    runReviewer (parallel)     runAnalyst          stage: analyst
    stage: reviewer                |
        |                          v
        |                      runDebate: Recruiter || Advocate
        |                          |               stage: debate
        +------------+-------------+
                     v
                 runJudge                          stage: judge
                     |
                     v
              insert tm_checks                     stage: done

    The main design idea is grounding: models may only cite evidence that
    code can verify.
        - Every resume line gets a stable id (L12) and agents must cite ids.
        - Claims whose quote is not on the cited line are dropped.
        - A requirement is downgraded to "missing" if its quote can't be
          found, and to "listed" if the proof isn't in Experience or
          Projects.
        - Code-measured skill evidence (lexicon regexes) overrides the
          model's reading.
        - The Judge's score is clamped between the two debaters' scores, and
          a failed gate forces "unlikely".
        - Job post and resume are wrapped in tags and declared data;
          injection-looking lines in the job post are flagged to the user.
        - Results are cached by sha256(prompt version + resume text + job
          text).

    Deterministic modules in lib/check:
        extract.ts    PDF -> lines, links, metadata, hidden text
        sections.ts   lines -> sections and bullets with ids
        lexicon.ts    skill names and regexes
        skills.ts     proven / listed / missing per job skill
        parrot.ts     phrases copied word for word from the job post
        style.ts      buzzwords, weak openers, no specifics, uniform length
        hygiene.ts    invisible characters, hidden text, metadata
        ats.ts        one page, contact info, sections, grad date, links
        jobText.ts    pasted text or fetched public job page
        index.ts      runDeterministic and the stuffing measure
        agents.ts     Analyst, Reviewer, Recruiter, Advocate, Judge

6.5 Resume Coach (/api/resume/improve, /summary, /draft)
    Rewrites bullets, writes the summary and prefills the builder, with
    prompts that forbid adding facts.


7. FRONTEND
-----------

/dashboard
    DashboardShell owns me, filters, stats and a refreshKey counter.
    Children bump refreshKey to make the stats and the feed refetch. Job
    decisions update optimistically and roll back on failure.

AI fit on job cards
    The feed joins tm_analyses, so cards with a cached analysis show their
    AI fit at once. Other cards request it automatically when they scroll
    into view, through lib/dashboard/analysisQueue.ts (two requests at a
    time; stops if there is no resume). The full analysis sits in a
    collapsed dropdown on each card.

Match score
    Computed in SQL on every feed and stats request: the share of the user's
    skills that appear as substrings of the job title plus description.

/check
    Reads the NDJSON stream with a ReadableStream reader and fills
    CheckReport stage by stage. ?auto=1 starts a run immediately.

/resume-builder
    Two steps: style, then details. ResumeDocument renders one fixed
    816x1056 page from a LOOKS config table of 10 styles. ScaledPage shrinks
    it for previews. PDF export is window.print() with print CSS that shows
    only #resume-print.

Styling
    Tailwind 4 plus a small set of classes in app/globals.css (.card, .btn,
    .input, .container-tm, .pill-gold). Cardinal and gold tokens on :root.
    Breakpoints at 734px and 1068px.


8. SCRIPTS AND TOOLING
----------------------

scripts/schema.sql        All nine tables.
scripts/setup_db.sh       Runs schema.sql against Neon; writes DATABASE_URL
                          and a generated SESSION_SECRET to .env.local.
scripts/set_gemini.sh     Saves GEMINI_API_KEY to .env.local and to Vercel
                          production.
scripts/set_mail.sh       Saves SMTP_USER and SMTP_PASS to .env.local.
scripts/classify_jobs.ts  Tags every job: one of 16 domains or "other",
                          level (student / general / experienced), and type
                          (internship / new_grad / full_time / contract /
                          part_time).
scripts/try_check.ts      Runs the deterministic checks on a local PDF and
                          job text file.

Build     next dev / next build, both with --webpack.
Tests     vitest with jsdom. Four test files: three in lib/auth, one in
          lib/check.
Lint      eslint with eslint-config-next.
PWA       app/manifest.ts (standalone, start_url /login) with icons in
          public/icons.
Fonts     Inter, Archivo and Archivo Black via next/font in app/layout.tsx.


9. WEAK POINTS
--------------

Server-side fetch of user URLs
    lib/check/jobText.ts:24 fetches any http(s) URL with redirects followed
    and blocks only LinkedIn and Handshake. There is no private-address
    filtering, so it is an SSRF vector.

Account pre-hijack
    Signup has no email verification, and Google sign-in links to an existing
    row by email (app/api/auth/google/route.ts:43). Someone who registers a
    victim's email with a password keeps access after the victim later signs
    in with Google.

Timeout budget
    Four attempts at 25 seconds each can exceed the route maxDuration (60
    seconds on most AI routes, 30 on improve and summary), and the check
    pipeline chains several such calls (lib/ai/gemini.ts:6).

Substring matching
    Short skills like "c", "r" or "go" match almost every job
    (app/api/dashboard/jobs/route.ts:41). The match is also recomputed across
    the whole jobs table on every request, with no index.

No rate limiting
    None on login, signup, forgot-password or any AI endpoint.

Two PDF extraction paths
    Upload stores text from extractText, while the check re-parses the
    stored bytes with readPdf, so the two can disagree.

Check history outlives the resume
    DELETE /api/resume clears tm_resumes, tm_analyses and the user's skills,
    but not tm_checks. Past checks, which contain the resume's lines, stay
    until each is deleted individually.

Dead or unfinished pieces
    - tm_email_codes is unused (scripts/schema.sql:82).
    - The tm_checks columns questions, answers, tailored and coach are never
      written. GET /api/check/[id] selects the first three, but the page
      ignores them.
    - The Judge's askStudent output is never shown.
    - JobFilters has minMatch, sort and level, but the UI has no controls
      for them.

Small bugs
    - SAMPLE_RESUME has a literal "\\n" in two project bullets
      (lib/resume/types.ts:122), so the preview shows "\n" instead of a line
      break.
    - public/brand/tommy-trojan.png and usc-logo.svg are referenced but not
      in the repo; BrandImage hides them silently.

Tests
    Only auth helpers and the deterministic checks are covered. There are no
    route or component tests.
